# CameraIntrinsics

An iPhone capture app for saving ARKit camera frames together with their per-frame camera intrinsics and, on supported devices, LiDAR scene depth. It provides manual capture, timed capture, photo review and ordering, and ZIP export through the iOS share sheet.

The app is written in Swift and SwiftUI using Apple frameworks, with no third-party package dependencies. Its current interface is in Chinese. It collects data for computer-vision and reconstruction workflows; reconstruction itself runs separately in the [RGB-D Point Cloud Workbench](../README.md).

## Features

- Capture an RGB image and its camera intrinsics from the same `ARFrame`.
- Save calibration JSON both as a sidecar file and in the JPEG EXIF `UserComment` field.
- Save unsmoothed `sceneDepth` and its confidence map when available.
- Capture manually or trigger a capture every two seconds.
- Preview saved photos, reorder them, and delete complete capture groups.
- Export the current batch as a ZIP without recompressing saved images.
- Share through AirDrop or save through the system Files interface.
- Start fresh batches and clear the app's local capture/export storage.

## Requirements and Installation

You need a Mac with Xcode and an iPhone that supports ARKit world tracking. LiDAR depth capture additionally requires support for the `.sceneDepth` frame semantic; the app checks this at runtime. The simulator cannot validate the real camera and LiDAR capture workflow.

1. Open `CameraIntrinsics.xcodeproj` in Xcode.
2. Select the `CameraIntrinsics` target and your connected iPhone as the run destination.
3. In **Signing & Capabilities**, select your development team. Keep the existing team and bundle identifier when reinstalling your own configured app; for a separate installation, configure signing for your account.
4. Check the target's iOS deployment setting against your device.
5. Press **Command+R** to build and install.
6. Launch the app and allow camera access.

The project contains a project-level iOS 16.0 setting, but the application target overrides it with `$(RECOMMENDED_IPHONEOS_DEPLOYMENT_TARGET)`. The effective minimum therefore depends on the Xcode configuration; do not assume the checked-in project necessarily installs on iOS 16 without checking the resolved setting. The target uses Swift 5 language mode and a portrait iPhone interface.

## Capture and Export

1. Open the app and wait approximately two seconds for warm-up. Autofocus remains enabled; this delay does not lock or guarantee focus.
2. Check the RGB resolution at the top of the preview and the LiDAR status below it.
3. Tap the camera button for one capture, or **Every 2 Seconds** (`每 2 秒连拍`) for timed capture.
4. Tap **Saved Photos · Preview and Order** (`已拍照片 · 预览与排序`) to review the batch. This stops timed capture.
5. Tap a thumbnail to enlarge it, drag the reorder handle to change export order, or use the delete control to remove a capture and its associated files.
6. Return to the camera view and tap **Package and Share** (`打包分享`). Export also stops timed capture.
7. Use AirDrop to send the ZIP to your Mac, or choose **Save to Files**.

Only one save is allowed at a time. If a save is still running when the timer fires, that trigger is skipped rather than queued. A capture also rejects a frame older than 0.5 seconds or the same frame timestamp as the preceding save attempt.

On a device with scene-depth support, a frame with missing depth is rejected so you can retry. On a device without that support, the app saves RGB and calibration only and explicitly marks depth as unavailable.

## Export Structure

A depth-enabled export has the following structure:

```text
CameraCaptures-<UUID>.zip
└── Captures/
    ├── README.txt
    ├── order.json
    ├── 1/
    │   ├── image.jpg
    │   ├── calibration.json
    │   ├── depth.json
    │   ├── depth.f32
    │   └── confidence.u8    # Only when supplied by ARKit
    ├── 2/
    │   └── ...
    └── ...
```

RGB-only captures contain `image.jpg` and `calibration.json`, without the depth files.

| File | Contents |
| --- | --- |
| `image.jpg` | JPEG encoded at quality 0.98, with calibration JSON in EXIF `UserComment` |
| `calibration.json` | Schema version 2, RGB intrinsics, image dimensions, timestamps, and depth availability |
| `depth.json` | Depth dimensions, format, units, source, intrinsics, and confidence-file reference |
| `depth.f32` | Tightly packed, row-major, little-endian Float32 depth in meters |
| `confidence.u8` | Tightly packed UInt8 confidence values at depth resolution |
| `order.json` | Mapping from export folder number to original capture ID |
| `README.txt` | Data interpretation notes generated by the app |

### Capture IDs and ordering

Each batch starts with capture ID `1`. A successful save advances the ID; a failed save does not consume it. Deleting a capture does not reuse its ID, and new captures are appended to the photo list.

Export folders are renumbered consecutively from `1` in the current list order. Sorting does not modify stored pixels or calibration. The `capture_id` in calibration JSON retains the original ID, and `order.json` records the mapping. For example, exporting capture `3` before capture `1` produces:

```json
[
  { "folder": "1", "original_capture_id": "3" },
  { "folder": "2", "original_capture_id": "1" }
]
```

Deleting or reordering photos does not change an already generated ZIP. Export again to create an updated archive.

## Camera Intrinsics and Image Coordinates

The RGB image and `frame.camera.intrinsics` are taken from the same ARKit frame. Calibration includes:

| Field | Meaning |
| --- | --- |
| `schema_version` | Export schema version; currently `2` |
| `capture_id` | Original capture number within the batch |
| `source` | `ARKit.ARFrame` |
| `image_width`, `image_height` | Stored image dimensions in pixels |
| `fx`, `fy` | Focal lengths in pixels |
| `cx`, `cy` | Principal-point coordinates in pixels |
| `K_rows` | Intrinsic matrix serialized by row |
| `frame_timestamp_seconds` | ARKit frame timestamp, not a calendar date |
| `export_requested_at` | ISO 8601 timestamp recorded when capture/save is requested |
| `exif_orientation` | `1` |
| `autofocus_enabled` | `true` |
| `depth_available` | Whether this capture includes depth |
| `depth_metadata_file` | `depth.json`, or `null` when unavailable |
| `distortion_coefficients` | `null`: distortion has not been measured |

The intrinsic matrix is represented as:

```text
K = [ fx   0  cx ]
    [  0  fy  cy ]
    [  0   0   1 ]
```

Use each image's own intrinsics. This app records ARKit-provided intrinsics; it does not perform a checkerboard calibration or independently estimate lens distortion. **A null distortion field does not mean zero distortion.**

### Resolution and orientation

The app captures ARKit stream frames using the default video format, rather than full-resolution still photos from the system Camera app. The actual stream dimensions are shown in the preview.

Saved images retain the native `capturedImage` pixel orientation. The app applies no pixel rotation, cropping, resizing, or additional geometric undistortion, and sets JPEG EXIF Orientation to `1`. Consequently, a photo captured while holding the phone upright may appear sideways on a computer.

The portrait preview may rotate or crop the image for display. Intrinsics correspond to the saved image pixels, not the preview layout. Any later rotation, resizing, or cropping requires the matching transformation of intrinsics and associated depth data.

Generic image viewers and reconstruction tools may not automatically recognize the custom EXIF JSON. Use `calibration.json` when integrating with other software.

## LiDAR Depth

The app enables `.sceneDepth` when supported and reads depth from the same `ARFrame` as the RGB image and calibration. It does not use `smoothedSceneDepth`, synthesize missing depth, or recover depth for previously captured RGB-only images.

- Depth represents **Z distance from the camera plane**, in meters, rather than Euclidean distance along the viewing ray.
- Nonfinite and nonpositive values are invalid.
- Confidence values are `0` (low), `1` (medium), and `2` (high).
- Confidence is optional in the capture app because the underlying confidence map may be absent.
- Depth resolution is recorded in `depth.json`; do not reshape it using RGB dimensions.
- Pixel-buffer row padding is removed before writing either binary file.

The app computes depth-grid intrinsics from RGB intrinsics using:

```text
sx = depth_width / rgb_width
sy = depth_height / rgb_height
K_depth = diag(sx, sy, 1) × K_rgb
```

Depth metadata records the frame timestamp, RGB and depth dimensions, `K_depth_rows`, and `temporally_smoothed: false`.

### Reading depth in Python

The following example requires NumPy and an extracted capture:

```python
import json
from pathlib import Path

import numpy as np

folder = Path("Captures/1")
meta = json.loads((folder / "depth.json").read_text())
shape = (meta["height"], meta["width"])
depth = np.fromfile(folder / meta["file"], dtype="<f4").reshape(shape)
valid = np.isfinite(depth) & (depth > 0)

if meta.get("confidence_file"):
    confidence = np.fromfile(
        folder / meta["confidence_file"], dtype=np.uint8
    ).reshape(shape)
    valid &= confidence >= 1

print("Depth dimensions:", depth.shape)
print("Valid medium/high-confidence samples:", int(valid.sum()))
print("Depth values in meters:", depth[valid])
```

## Using Captures with the Point Cloud Workbench

Transfer the exported ZIP to the computer running the [workbench](../README.md), then upload the ZIP or its extracted capture folder through the browser interface.

The current workbench requires more than the capture app itself:

- Every capture must have RGB, calibration, depth metadata, depth values, and a confidence map.
- Captures must satisfy the workbench's schema, timestamp, intrinsics, and data-validation rules.
- Normal batches require 10–200 captures. Batches of 3–9 require the small-batch diagnostic option.
- The upload limit is 2 GB decimal, with additional per-file limits.

An RGB-only export, or a depth export without `confidence.u8`, cannot be used directly by the current workbench. Its importer is described as the Captures4 format; the camera app's ZIP root is named `Captures`, which the workbench can accept. You do not need to rename it solely to match the fixture name.

## Batches, Storage, and Cleanup

Captures stay in the app's Documents directory until exported or deleted:

```text
Documents/
└── CaptureBatches/
    ├── batch_<UUID>/
    │   ├── README.txt
    │   ├── 1/
    │   └── ...
    └── Exports/
        └── CameraCaptures-<UUID>.zip
```

A serial writer queue manages storage. Each capture is written into a staging directory and committed by renaming it into the batch only after saving succeeds. Before committing, the app reads the JPEG back and verifies its embedded JSON and dimensions.

**Reset Camera · Start New Batch** (`重置相机 · 开始新一批`) clears the displayed count and share reference, resets numbering, and selects a new batch directory. It preserves older batches on disk. Restarting the app process also creates a new batch; going to the background and returning within the same process continues the current batch, with timed capture stopped.

There is currently no history browser or export entry for older batches. Export the current batch before resetting or closing the app process if you need access through the interface. Every export creates a new ZIP, and older ZIPs remain stored. Uninstalling the app removes its local data.

**Clear All Local Photos and ZIPs** (`清理全部本地照片与 ZIP`) asks for confirmation, then deletes current and historical capture storage, legacy `Captures` and `Exports` directories, and pending data owned by this workflow. It starts a fresh batch afterward. This is permanent; files already transferred to a computer or saved elsewhere are unaffected.

## Verification

From the `CameraIntrinsics` directory, run the synthetic storage checks on a Mac:

```sh
python3 tests/run_storage_checks.py
```

The runner extracts the app's storage implementation, combines it with synthetic tests, and executes Swift through `xcrun`. It defaults `DEVELOPER_DIR` to `/Applications/Xcode.app/Contents/Developer` if that variable is not already set. For another Xcode location:

```sh
DEVELOPER_DIR="/path/to/Xcode.app/Contents/Developer" \
  python3 tests/run_storage_checks.py
```

The checks cover:

- JPEG embedded JSON and sidecar consistency.
- Synthetic image orientation and rejection of mismatched dimensions.
- ZIP integrity and exclusion of failed captures.
- Batch isolation and reordered image/calibration pairing.
- Deletion, new captures after deletion, and contiguous export numbering.
- Storage cleanup while preserving unrelated files.
- Float32 depth values, removal of row padding, confidence bytes, and depth inclusion in ZIPs.

These checks do not exercise live ARKit acquisition, camera permissions, UI interaction, AirDrop, or physical LiDAR accuracy/alignment. Previous project notes report successful unsigned iPhoneOS builds and synthetic tests; those results are historical, not a new validation run performed by updating this README. Verify the workflow on a real device before a large capture session.

## Troubleshooting

| Symptom | Action |
| --- | --- |
| Camera access is denied | Allow camera access for the app in iPhone Settings. |
| The app reports unsupported ARKit | Use a real iPhone supporting ARKit world tracking. |
| LiDAR is unavailable | RGB-only capture is supported, but depth reconstruction requires a device supporting scene depth. |
| A supported device reports a missing depth frame | Wait for a depth frame and capture again. |
| Timed capture saves fewer images than expected | Busy saves and unavailable/stale frames can skip timer triggers. |
| Photos appear sideways on the computer | This is the saved native sensor orientation; transform intrinsics if you rotate the pixels. |
| Intrinsics are not visible in an image viewer | Read `calibration.json`; the viewer may not expose EXIF `UserComment`. |
| Old photos are absent after resetting | Reset selects a new batch. Older data is retained, but the UI has no historical-batch export entry. |
| A shared ZIP has an earlier order or deleted photos | Generate a new ZIP after changing the batch. |
| The camera session is interrupted or fails | The app stops capture; the reset control starts a new batch, so export the current batch first if needed. |
| Saving or exporting fails | Review the displayed error and check available device storage. |

## Scope and Limitations

This is a data-collection tool, not a complete calibration, reconstruction, or measurement application. It does not export ARKit camera poses, independently measure lens distortion, lock autofocus, guarantee two-second capture intervals, or validate physical depth accuracy. Capture order and timestamps are exported, but reconstruction and quality assessment belong to downstream processing.

The implementation stores data locally and has no application-level cloud upload service. External transfer is initiated by the user through the iOS share sheet.
